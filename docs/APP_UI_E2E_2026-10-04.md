The repository serves a pilot dashboard at `/pilot` and a document workflow at `/workflow-run`. The pilot dashboard is a separate page with bearer-gated data APIs, but it is still a static HTML/JavaScript shell served by the same FastAPI site. The document workflow remains a public site page, not an integrated tenant workspace in the pilot dashboard. ### Upload → decision → remediation

Posted a synthetic steel CSV through the running `/api/workflow-run/parse` endpoint. It returned one line, with CN source cell `B2` and a document SHA-256. Compiling with an unverified commercial invoice returned `BLOCKED`; after the fix made during this check, the response includes `COMMERCIAL_INVOICE_UNVERIFIED` in its blocker list. Marking that synthetic evidence verified returned `READY`, with compiler `READY_FOR_SUBMISSION` and entitlement `ENTITLED` when the **synthetic 0% TARIC seed and demo CBAM pack** were enabled. These states demonstrate the UI workflow only; they are not client clearance or real regulatory evidence. The workflow response is in-session and does not persist the uploaded PDF/CSV or a correction chain.

### PDF checks

- Parsed `data/client_data/scribd-797969813.pdf` locally, without sending it to a model. Text parsing returned HTTP 200, but the strict extractor produced zero shipment lines and `PDF_LINE_ASSOCIATION_UNVERIFIED`; three broad CN hints were kept only as hints.
- Ran an authenticated model-assisted upload with a wholly synthetic one-page PDF. An unauthenticated model request returned HTTP 401; the authenticated request returned HTTP 200. The deterministic PDF parser produced one candidate, but the model returned no verifiable line on this run. The candidate remained `BLOCKED` because destination was missing, with no bounding-box provenance. This is a safe failure, not a successful model extraction.
- Automatic approval review rejected sending the real `client_data` PDF to the model gateway because its contents could be sensitive and the user had not specifically authorized that transfer. No real PDF contents were sent to the gateway.

## Fix made during this check

The workflow previously returned `BLOCKED` for unverified evidence but an empty `blockers` array, leaving the UI unable to explain the decision. `app/content_pages.py` now includes named evidence-state blockers. A regression test covers this case, and the live session confirmed `COMMERCIAL_INVOICE_UNVERIFIED` appears before remediation and clears afterward.

## Remaining gaps for a client-facing app

1. The ingestion workflow is linked from the public content navigation, not housed in the pilot dashboard. Pilot authentication gates model calls and data APIs, but `/workflow-run` itself is a public shell with in-session state.
2. The pilot dashboard currently displays synthetic seeded data. A client tenant cannot yet use this session to ingest its own documents and see persisted shipments, evidence lineage and remediation history in `/pilot`.
3. The PDF path lacks reliable table-cell coordinates and cross-document row joins. The model is only an assistant; on this synthetic run it did not add a verifiable proposal.
4. A browser interaction and visual rendering pass is still needed. HTTP, API and JavaScript syntax checks cannot establish layout, file-input behavior, console health or accessibility in real Chrome.

After the fix, the full repository suite passed **240 tests**. The local session was stopped after verification. A real-document model test requires explicit approval for a specified file and gateway destination.
